# v2.7.7 · 更新判定逻辑下沉到 core，补 11 项单测

## 做了什么

v2.7.6 加的「启动时检测新版本」，判定逻辑原本写在 `apps/mobile/src/platform/update-check.ts`
里。这段逻辑没有平台依赖（不碰 fetch、不碰 kv、不碰 Linking），但它决定了
**要不要提示用户有新版本** —— 最容易写错、又最难在设备上复现的地方
（得先真有一个更高版本的 release 才能看到提示）。

现在挪到 `packages/core/src/updates.ts`：

| 函数 | 职责 |
|---|---|
| `compareVersion(a, b)` | 语义化版本比较，按段比而非按字符串（`2.7.10 > 2.7.9`） |
| `readPendingUpdate(kv, current, fallbackUrl)` | 从 kv 判定该不该提示，含两条防御 |
| `shouldAutoCheck(lastAt, now, interval)` | 一天一次的节流判定 |

移动端的 `update-check.ts` 现在只做平台的事：请求 GitHub API、读写 kv。
判定全部委托给 core，两处不会漂移。

## 补的单测（11 项）

`packages/core/src/__tests__/updates.test.ts`

- **版本比较**：按段比（`2.7.10 > 2.7.9`、`2.10.0 > 2.9.0`）、容忍 `v` 前缀、
  段数不一致按 0 补、非数字段当 0 不抛异常
- **要不要提示**：无记录不提示；记录更高时提示并带 url；没有 url 回落默认 release 页；
  **记录不比当前新就不提示**（用户可能已手动装新版，这时再弹横幅就是骚扰）
- **节流**：从没查过就查；一天内不重复查；超过一天就查

## 为什么要单独发一版

不是为了改行为 —— 行为在 v2.7.6 已经和设备验证过（12/12）。
是给这段逻辑留下可回归的护栏：以后改版本号规则、改节流间隔，跑 `bun test` 就知道有没有破坏。

顺带解决一个验证盲区：v2.7.6 时「有新版」这条 UI 分支没法验（release 包不可调试，
`run-as` 被拒，伪造不了 kv；也不可能为了测试造一个假的更高版本 release）。
现在 v2.7.7 发布后，装上 v2.7.6 的包，它自然会把 2.7.7 认成新版 —— 横幅可以真实验证。
